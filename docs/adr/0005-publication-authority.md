# ADR 0005: Independent approval and a separate catalogue delivery branch

Status: accepted for implementation. The production GitHub App, branch rules and deployment are external release configuration, not implied by repository access.

A private SQLite approval binds immutable submitted content, current independent reviewers, reviewed runtime records, policy and exact publishable bytes. The public receipt is only a reference. The trusted OmaStore GitHub App checks the proposed registry, media and receipt against private authority and rejects additional changed files. Contributor-controlled CI, labels, receipts and prose cannot grant approval. Normal code-only pull requests do not need application approval.

The product authenticates as an operator-owned GitHub App. A private RSA key creates a short-lived RS256 JWT; installation tokens are scoped to the configured repository and refreshed before expiry. Keys and webhook secrets are read from private files. Coding-agent connector credentials never become product credentials. Signed webhook bodies are verified before decoding and delivery IDs are deduplicated.

Public intake begins only after the author confirms the exact submission preview. It includes the immutable candidate and public digest, excluding drafts, account/session details and reviewer-only observations. A lost issue-create response enters read-only reconciliation, preserving one logical intake. Deterministic branch names, persisted checkpoints and PR lookup make publication retries recoverable. Unknown external outcomes stay visible for reconciliation.

A source catalogue PR merges into the configured publication branch, initially `main`. A separate `catalogue-live` branch is the native delivery surface. Only the product App may advance it under protected-branch rules, after checking current approval and exact content again. This prevents a merged source PR or a stale check during a provider outage from immediately becoming the client catalogue. An App-generated fast-forward delivery commit preserves previously delivered unrelated entries. No force push is used.

The service validates a live-branch snapshot before atomically replacing its local public catalogue file. A failed validation, fetch or replacement preserves the prior file. A record becomes `published` only after the deployed public HTTP API reports the approved content. Source PR, merged commit, live branch and observed public revision remain distinct records. A provider outage cannot be treated as successful delivery.

Published entity provenance controls updates. A new author cannot overwrite an existing listing or maker merely by reusing its ID. Unclaimed community nomination and verified publisher control remain separate; initial listing stewardship is not seller identity. Project identity changes require renewed review rather than a silent source swap. Shared setup context does not transfer listing stewardship.

The configured check must require the specific product App as its source. An unconfigured branch rule is not a passed release gate.
