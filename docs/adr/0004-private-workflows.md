# ADR 0004: Private workflows and full-scope continuation

Accepted engineering direction, 8 September 2026. Tom authorised implementation of every scoped bundle, regular commits and autonomous engineering decisions. Missing deployment credentials, participant evidence or Omarchy hardware are verification/configuration gates, not reasons to omit implementation. Real charges and unsupported machine writes remain disabled under the product's release contract.

Use Axum 0.8, Tokio, rusqlite 0.40 with bundled SQLite, and reqwest 0.13 with Rustls. Versions were checked against the maintained primary documentation; Cargo.lock records the resolved versions. The private database uses transactional additive migrations, foreign keys, WAL, full synchronous commits and owner-only files. Database work runs outside the asynchronous request executor. Roles are rechecked on mutations and are not frozen into bearer tokens.

GitHub browser sign-in uses the documented authorization-code flow with random state, S256 PKCE and an exact operator-owned HTTPS callback. A separate desktop challenge binds the completed login to the initiating client. Callback state and completed login delivery are single-use and expire. Provider tokens stay server-side during identity lookup and are not stored in the workflow database. OmaStore sessions are stored as hashes; the desktop keeps its token in Secret Service, with explicitly disclosed session-only operation if the keyring is unavailable. Sign-in alone grants no project claim. Reauthentication does not restore a revoked role.

Project control uses a scoped, expiring published challenge: a canonical GitHub repository's `.omastore-claim.json`, or a publisher origin's `/.well-known/omastore-claim.json`. The challenge binds account, target, issuer and nonce. Fetches validate HTTPS and every DNS address, pin the checked addresses, disable proxies/redirects and enforce deadline/decompressed-byte limits. An active claim by another account requires an ownership review. Claims expire after 30 days and must be revalidated before sensitive publication changes.

The native UI continues the existing Qt composition. Author/reviewer views call a bounded authenticated command API through the core. No browser UI or operator database editing is required for ordinary author/reviewer actions. A local CLI bootstraps reviewer/operator roles after an actual account exists. Development identities are compiled only with an explicit development feature and require a separate loopback sandbox mode; they can never activate real publication or commerce adapters.

Implementation proceeds as reviewable B04–B09, B10–B16, B17–B19 and B20–B22 groups, with suffixed commits for substantial native/service slices. Pilot recruitment, real Omarchy runs, provider registrations, independently reviewed commercial responsibilities and provider sandbox receipts remain explicit evidence columns. No fixture becomes a public listing or release sign-off.

Primary references: [GitHub OAuth and PKCE](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps), [Axum](https://docs.rs/axum/0.8.9/axum/), [rusqlite](https://docs.rs/rusqlite/0.40.2/rusqlite/), [reqwest](https://docs.rs/reqwest/0.13.4/reqwest/).
