# Selective desktop settings

Open Library → Desktop settings, or Review desktop settings on a setup. Choose supported fields explicitly, then preview the current value, desired value, affected scope and restoration limits. Previewing saves a local proposal; it does not authorise a desktop change. Unknown versions, custom bars, missing/duplicate clock widgets and unsafe configuration files are explicit unavailable states.

The initial registry contains `omarchy-theme` revision `1` and `omarchy-clock-placement` revision `1`. Theme values are `tokyo-night` and `catppuccin` for public references; sample mode offers only `sample-ink` and `sample-sand`. Clock values `left-start`, `center-start` and `right-start` select index zero in that section. The widget's options and all other shell fields remain outside the requested change.

Native IPC: `settings.adapters` takes empty parameters. `settings.preview` takes `{settings:[{adapter,valueId,revision}]}` with one or two distinct known adapters. `settings.get` accepts a saved proposal `{id}`. Proposals expire after ten minutes, bind the current environment/file identity and remain local. The live version allowlist is empty until real Omarchy evidence passes. See ADR 0008 for exact source grounding and ownership boundaries.


B18 implements explicit apply, private per-setting before/after journals, durable interruption states, compare-before-write checks, and restoration previews. Repeating the same confirmed plan returns its existing receipt. Repeating a recipe builds no-op effects for values already present. A separate confirmation authorises restoration only when the current selected value still equals the applied value; unrelated current configuration and clock options survive. Layout changes that invalidate a previous position stay conflicts. Unknown outcomes require observation/reload reconciliation; failures never become successful receipts merely because a file write started.

Reads walk directory handles without following symlinks. Temporary creation and atomic rename are relative to one verified directory handle; files and their parent are synced, mode bits preserved, and only the current operation's unique temporary file is removed. A concurrent unrelated writer cannot participate in an atomic compare-and-swap without a shared locking protocol; live desktop evidence must exercise Omarchy's own writer/reload interactions and ACL expectations before enabling a release. The sample file contract is complete; the live allowlist is empty. Theme application remains gated because a theme name alone cannot represent its generated effects.

The fixed future clock reload uses `omarchy-shell shell reloadConfig`, expects the documented `ok` reply, passes only desktop IPC variables, and keeps errors in the recoverable journal. Its executable resolution and customised-desktop behaviour still require actual target evidence. Application/setup detachment never implicitly restores settings or removes personal files.
