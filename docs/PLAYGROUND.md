# Explore the native playground

Build with `./bin/build demo`, then run `./build-demo/bin/omastore --demo` on Linux. The Qt application talks to its sibling Rust core; the local fictional workflows need no server or payment account. Keep the two executables together. Demo state is private and separate from the ordinary build, and survives a restart.

1. **Discover.** Search the six fictional apps, inspect source/licence/cost/privilege evidence, save one, and visit its maker. Empty public shelves remain empty in the ordinary build.
2. **Choose a setup.** Open Setups → Writing desk, inspect required and optional pieces, change the selection, and preview the exact resulting installation plan. Export/import preserves the selected public recipe and attribution.
3. **Rehearse installation.** In the sample plan, give explicit consent to the independent operation worker. Library shows the recorded result. Exercise interruption reconciliation, explicit removal and the reviewed diagnostic export. Sample effects stay inside the private fixture installation database.
4. **Try selective settings.** Open the settings preview from Library or a setup, inspect before/desired values and scope, and give separate consent. History supports explicit restore with conflict detection. Sample settings never change the host desktop. Theme changes remain previews until an actual Omarchy adapter is verified.
5. **Make a remix.** Keep the setup pieces/settings you want, save a named local remix, inspect current-machine differences, and export or create an attributed private author draft. Importing is not installation.
6. **Submit and review.** Submit → Author workspace supplies fictional author, reviewer and operator sessions. Create a private draft, inspect media and exact submission preview, submit an immutable revision, then use an independent reviewer session for checks/evidence and approval. Publication rehearsal records observed delivery before the app or release feed changes. A fictional publication is not a GitHub merge.
7. **Review commercial readiness.** Sign in as the fictional operator. Author workspace → Commerce shows every missing launch fact. Enter a reason and allow test purchases. This changes only sample purchase availability.
8. **Buy and recover.** Library → Purchases and licences offers fictional perpetual, service and subscription products. Review the frozen price and terms, consent, and simulate payment. The failed-delivery option deliberately leaves a paid order visible for retry. Perpetual licences export and verify offline against the separately pinned sample issuer.
9. **Refund.** A paid receipt shows completed refunds and the remaining amount. Enter an amount/reason and request it. A current operator separately reviews and approves or rejects it. Completion and the platform-fee reversal have separate states. For example, a GBP 2.00 partial refund of the fictional GBP 10.99 perpetual order reverses GBP 0.08 of the original GBP 0.49 platform fee. The final refund reverses the remainder.
10. **Inspect author finances.** Commerce → Sales and provider records → Load my commercial sellers → Reconcile. Read per-currency recorded proceeds, accounting reserves, observed provider cash, processing-cost gaps, disputes and payout failures. The whole provider account may contain outside-store income. Nothing here starts a bank payout.
11. **Rehearse support.** As operator, open an order, record a private support note, or select a fictional payout/dispute/delayed-refund scenario. Retrieve the current dispute, record an evidence report/digest, preview and save the private packet. Submitting that packet to a real provider remains the responsible operator's action.
12. **Renew or cancel.** For a paid fictional subscription, create the renewal scenario against its original order and refresh billing. It creates a separate provider-confirmed invoice/receipt; a future period waits before delivery. Cancel future billing with explicit consent. Earlier receipts, signed licences and local documents remain. New renewal scenarios are rejected after the fictional provider confirms cancellation.

For a real Stripe test-account rehearsal, use the separate service/database/configuration in [COMMERCE.md](COMMERCE.md). The desktop needs an independently reviewed issuer trust pin. A successful fictional rehearsal does not replace that provider report.

All planned B00–B22 software paths are implemented. The public-pilot and live adapter/payment gates remain closed until real Omarchy desktop/lifecycle evidence, actual publisher participation, the appointed operator's commercial responsibilities, provider approval and an end-to-end provider sandbox report exist. The [bundle status](BUNDLE_STATUS.md) and [handoff receipts](BUILD_HANDOFF.md) distinguish those external gates from implemented code.
