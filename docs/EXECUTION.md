# Native package execution

Managed execution is implemented behind an explicit release evidence gate. `VERIFIED_OMARCHY_RELEASES` in the local core is empty: no real Omarchy lifecycle report has been supplied. There is no environment or IPC bypass. The development build provides a complete, labelled package rehearsal using its separate private database. The normal system chooser and updater remain explicit external handoffs.

A confirmation includes the exact saved proposal ID/digest and an affirmative gesture. The core recomputes its catalogue/status/host/dependency material before recording consent. The worker rechecks after the normal terminal sudo prompt, including the ten-minute expiry. Stale, changed, untrusted or incomplete plans cannot begin a package transaction. Replay returns the existing operation and never creates a second package transaction.

The pipe core starts a separate worker using its own executable and fixed arguments. Live workers run in `omarchy-launch-terminal`; sample workers have a separate process group and no terminal or package-manager access. Closing the native window or killing its coordinating core does not terminate the worker. Kernel file locks and an atomic claimed flag prevent competing workers; a PID alone is never evidence that an operation is alive.

The live adapter validates root-owned absolute executables and builds argument arrays for `sudo -n -- /usr/bin/pacman -S --needed --noconfirm -- REPOSITORY/PACKAGE=VERSION`. Authentication is an earlier `sudo -v` in the system terminal. Credentials never enter the Qt bridge, application input capture or logs. The adapter does not refresh package databases, upgrade dependencies independently, disable signatures/dependency checks, overwrite files, or execute author-supplied shell text. Updates go through the fixed `omarchy update` handoff.

An operation progresses from `planned` through `awaiting_user` and `running` to `succeeded`, `failed` or `unknown`. A running transaction has no timeout or cancellation kill. Cancel before that durable execution boundary prevents a package write; after it, the UI says that the current transaction must finish. The worker continually drains package output with a bounded retained diagnostic prefix, stores only fixed result codes, and keeps its heartbeat separate from the append-only event sequence. Package-manager locks, privilege denial, unavailable repositories and unknown outcomes have distinct codes.

Success requires observed app and resolved dependency versions, an unlocked known package state, a successful process result and unchanged configuration/repository database fingerprints. Recipe outcomes remain per component: an external/manual component does not become installed when managed components succeed. Installed observations preserve whether a component pre-existed and which setup references it. B15 adds recovery, selected retry, explicit removal and diagnostic export to this durable foundation.

Validation includes argument-injection cases, changed/denied consent, duplicate claims, cancellation boundaries, kernel locks, event replay, native keyboard consent and an actual subprocess test that kills the coordinator after confirmation, reconnects and observes exactly one completed fictional installation. This is process evidence on Linux, not a real package installation. The release gate still needs a clean Omarchy VM install, terminal authentication/denial, repository outage, lock, cancellation, source/version observation and GUI-loss cases for each enabled release.
