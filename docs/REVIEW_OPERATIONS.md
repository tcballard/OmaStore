# Submission checks and review

The author service runs one checks dispatcher every five seconds when a private workspace is configured. SQLite leases coordinate multiple service processes. Set `OMASTORE_CHECKS_PAUSED=1` to pause dispatch while retaining queued records and findings. A worker gets a 120-second lease, performs bounded reads, then commits findings only if it still owns that lease. Crashed leases can be retried four times; later retries require an explicit author/reviewer action.

A check reads a frozen candidate. It never checks out or executes submitted code, builds, dependency scripts or hooks. Public HTTPS reads pin checked DNS addresses, disable proxies and redirects, and cap decompressed text at 1 MiB. Links have a fixed count and time budget. GitHub commit and official Arch package metadata comparisons report a changed or unavailable identity honestly. A package version or source commit does not establish the hash of executed bytes.

Every finding records the candidate revision, actor, check, tool version, result, timestamp and bounded explanation. `unavailable` is distinct from `fail` and `pass`. An informational nomination can remain unclaimed; signing in cannot confer publisher control. Media rights assertions require human review even after safe image/video processing.

For runtime evidence, use a disposable Omarchy VM with no author-service, GitHub, SSH, signing or payment credentials. Record the exact downloaded/built/executed SHA-256, immutable release identity, candidate digest, Omarchy and package versions, architecture, display/session environment, tool version, actual test time, tester ID, observations and limitations. Exercise installation, launch, supported update or explicit updater handoff, and removal while checking that personal files remain. Keep raw logs private; place only the reviewed public evidence summary at the report's HTTPS evidence link.

Import a `RuntimeEvidence` JSON file through the native reviewer workspace. The strict shape is defined by `crates/workflow/src/checks.rs`: `revisionId`, `revisionDigest`, `appId`, `record` (the catalogue `TestRecord`), and `install`, `launch`, `updateOrHandoff`, `removal` observations. A reviewer must import it; the revision's author cannot test their own submission for this approval path. Reports are immutable and name the actual tester. Corrections require a new report from another tester or a new candidate, preserving the original record.

The sample build has an explicit “Run sample checks” action. Its records say they are simulations, live in a development-marked database, and cannot be used by a production publisher. This is useful for exercising state transitions; it is not Omarchy VM evidence.

Sources inspected: [GitHub commit API](https://docs.github.com/en/rest/commits/commits#get-a-commit), [GitHub webhook validation](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries), and [FFmpeg MOV demuxer options](https://ffmpeg.org/ffmpeg-formats.html#mov_002fmp4_002f3gp). FFmpeg disables external track references and absolute external paths by default; OmaStore also restricts input protocols and demuxers, process resources, wall time and output size.
